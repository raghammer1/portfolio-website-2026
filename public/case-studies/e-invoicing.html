UNSW CAPSTONE · FULL STACK

From invoice documents to structured workflows

I implemented a MERN e-invoicing application for a university team capstone, connecting document extraction, UBL XML conversion, validation, storage and sharing. The project is historical; I do not claim current production adoption or a verified live deployment.

Problem and role

The application brought invoice conversion and validation into one web workflow. I implemented the application within a six-person university team project. The current public repositories contain commits under Raghav Agarwal and raghammer1; substantial code was imported in the initial commits, so the history is useful for specific changes rather than a complete reconstruction of development.

Architecture

A React interface calls an Express API. The backend coordinates PDF extraction through Veryfi, converts extracted JSON into UBL XML, stores documents with MongoDB/GridFS and invokes an external UBL validator. Separate routes support authentication, profile editing, document access, report generation, sharing and email history.

Technical decisions and constraints

External extraction and validation APIs provide specialised document capabilities, while the application manages the user workflow and stored records. GridFS keeps binary documents in the MongoDB storage stack. Those choices introduce provider availability, response-shape and access-control concerns. The course report records an approved extraction-provider substitution, but it does not establish my personal decision process, so I do not invent a comparison I cannot reconstruct.

The backend includes five Jest files covering authentication, password reset, file retrieval and email history. Cypress browser-test source exists in the frontend. Test presence is distinct from current pass status: some tests connect to the configured database and create or delete records, so they were not run against historical services. No measured coverage percentage is claimed.

Risks and limitations

This is a capstone application rather than a certified compliance or security product. Historical URLs, dependency age, external API credentials, document authorisation and test isolation require review before reuse. Original project documentation is not distributed because it contains sensitive configuration material.

Result and next steps

The source contains an end-to-end application structure for conversion, validation and sharing. No customer count, financial saving or error-rate metric is available. Next work would use disposable test services, provider mocks, malformed-document fixtures, consistent environment configuration and a route-by-route ownership review before any new deployment.
